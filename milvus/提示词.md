# 任务：打造一个「Milvus × RAG 执行链路」交互式拆解页

你现在是一名前端工程师、检索系统工程师，同时也是能把复杂流程画清楚的技术插画师。

请围绕一个具体问题，做一个**单页、零依赖、可离线打开**的交互式拆解网站：

> **在 RAG 应用里，Milvus 到底在哪一步出现、收到了什么、做了什么、又把什么交回给应用？**

这不是一篇「Milvus 是什么」的介绍页，也不是把官方文档搬成网页。它应该像一次**带调试器的执行追踪**：你给一句提问，然后一站一站往前走，看应用侧做了什么、SDK 发出了什么请求、请求在 Milvus 集群里经过谁、返回的候选怎么被归并和重排、最后怎么变成 LLM 的上下文。每一步都可以改参数，数字跟着变。

**核心目标：让一个没搭过 RAG 的开发者，走完十站之后能准确说出「Milvus 负责哪一段、不负责哪一段」。**

## 二、两条链路，十个站点

整个页面按「先写进去、再查出来」组织，顶部是一条十站的进度轨道，左边窄右边宽：左轨是站点列表（带阶段分组），右侧是当前站的完整内容。

- **阶段 A · 写入链路**：文档怎么变成 Milvus 里可检索的数据
- **阶段 B · 查询链路**：一句提问怎么变成 LLM 手里的上下文

| # | 站点 | 站内一句话 | 这一段谁负责 |
| --- | --- | --- | --- |
| 1 | 切分 Chunk | 把文档切成能被检索的最小单元 | 应用侧 |
| 2 | 向量化 Embed | 文本变成定长向量，维度从这里定型 | 应用侧（真实模型）/ 页面用示意向量 |
| 3 | 建模 Schema | 决定哪些字段能过滤、哪些能全文检索 | 应用侧设计，Milvus 执行 DDL |
| 4 | 建索引 Index | 选索引类型与距离度量，决定「快」和「准」怎么换 | Milvus（Coordinator 下发，Data Node 构建） |
| 5 | 写入与可见性 | 数据从 WAL 到 growing 再到 sealed，什么时候查得到 | Milvus（Streaming / Data / Query Node） |
| 6 | 查询向量化 | 用同一个模型把问题变成同一空间里的向量 | 应用侧 |
| 7 | 检索路由 | 请求经过 Proxy，落到 Streaming 与 Query Node，再逐级归并 | Milvus（Access / Streaming / Query） |
| 8 | 过滤与分区 | 元数据条件在检索里生效，而不是查完再筛 | Milvus（filtering search / partition） |
| 9 | 混合检索 | dense 与 BM25 两路结果融合成一份候选 | Milvus（`hybrid_search` + ranker） |
| 10 | 重排与生成 | 重排、塞进 token 预算、带上引用，交给 LLM | 应用侧（重排可用 PyMilvus 集成） |

十站里，**1、2、6、10 是应用侧的事，3、4、5、7、8、9 是 Milvus 的事**。这条分界线要在每一站都看得出来 —— 页面用两条主泳道（应用侧 / Milvus 侧）表达，Milvus 侧再分接入、执行、存储三层，而不是靠文字说明。

## 三、每一站都必须出现的四段式

不管哪一站，正文都给这四块，顺序固定：

1. **应用侧做了什么** —— 真实的方法名与参数（`milvus_client.insert(...)`、`hybrid_search(...)`），参数值跟着页面控件走。
2. **请求走到了哪** —— 结合 `architecture_overview.md` 的路径：`Access Layer → Coordinator` 还是 `Access Layer → Streaming Node` 还是 `Access Layer → Query Node`，画成时序或泳道，节点名用原文。
3. **返回了什么** —— 结果的数据形状：`ids`、`distance`、`entity`、`cost`，或 `insert_count`；用真实结构而不是「结果列表」四个字。
4. **动手改** —— 至少 2 个可调参数，改动后**页面上的数字必须真的变**。只改颜色、不改数字的控件一律删掉。

另外每站右下角放一个「可复制的 PyMilvus 片段」，代码随参数实时生成（比如把 `limit`、`ef`、`consistency_level` 拼进去）。代码只作展示，不联网、不执行、不出现任何真实密钥或端点。

## 四、逐站要求

### 站 1 · 切分 Chunk

- 左侧显示原始文档（可滚动），右侧显示切出来的块；块用颜色区分来源文档，点击块高亮对应的原文区间。
- 每块必须带：`id`、字符数、标题路径、`source`、`dept`、`version`、`updated`、`acl`。这些元数据不是装饰 —— 站 8 的过滤全靠它们。
- 可调：块大小、重叠、是否「按标题切」。
- 真算：块数、中位长度、实际重叠字数、元数据覆盖率。
- 一句话结论：**切分是应用侧的事，Milvus 不管切分；但切坏了，后面所有指标都会跟着坏。**

### 站 2 · 向量化 Embed

- 展示「文本 → 向量」的降维投影（三维空间或二维散点），点按主题聚簇，悬停显示所属块。
- 可调：归一化开关、维度截断（比如 1024 → 64）。
- 真算：两个向量的余弦与内积；并演示**归一化之后 COSINE 与 IP 给出同一排序**这个数学事实。
- 必须标注：这里的向量是**确定性示意向量**（同主题靠近、带可复现噪声），不是真实 embedding 模型输出，图上的距离不代表语义真值。把构造方式写进 README。

### 站 3 · 建模 Schema

- 给一份集合定义表，字段固定为：
  - `id` INT64 主键
  - `dense` FLOAT_VECTOR（维度与站 2 一致）
  - `text` VARCHAR + `enable_analyzer=True`（BM25 的输入）
  - `sparse` SPARSE_FLOAT_VECTOR（由 BM25 Function 产出）
  - 标量：`source`、`dept`、`version`、`updated`、`acl`
- 展示对应的 `create_collection` / schema 定义（含 `max_length`、动态字段开关），代码可复制。
- 可调：是否启用 BM25 字段、是否开启动态字段、主键类型。
- 真算：切换这些开关后，站 9 的混合检索是否还有两路、站 8 的过滤是否还能用 `acl`。
- 必须讲清：**Schema 决定了「能过滤什么、能全文搜什么」，改 Schema 是唯一需要重建集合的步骤。**

### 站 4 · 建索引 Index

- 一张索引对比表（至少 FLAT、HNSW、IVF_FLAT、DISKANN），列：适用规模、是否占内存、召回特点、可调参数。
- 参数区：`M`、`efConstruction`（HNSW）或 `nlist`（IVF），以及 `metric_type`（COSINE / IP / L2）。取值范围与默认值以官方 Index 页为准，页面写「文档出处」，不要凭印象填数。
- 真算：构建出的图或倒排结构、每个点的邻居/所属簇、内存估算（写出简化公式，别假装是精确值）。
- 必须出现一句边界说明：**索引只影响「多快找到」和「找得准不准」，不改变向量本身。**

### 站 5 · 写入与可见性

这是全页最重要的一站，必须把 `architecture_overview.md` 里的 Insert 数据流完整还原：

```
Client → Proxy(Access) → Streaming Node → WAL 落盘 → growing segment 可查
                                        ↓ 段满/达到条件
                                   sealed segment → Data Node 做 compaction 与建索引
                                        ↓
                                   Object Storage ← Query Node 按需加载
```

- 做成一条**可播放的时间线**：点「插入 1 批数据」，看这批数据从「已提交」到「growing 可查」到「sealed」到「索引就绪」的位置变化。
- 可调：一致性级别（Strong / Session / Bounded / Eventually）、批量大小。
- 真算：给定「插入完成后 t 秒」，四档一致性下查询能否看到这批数据；把结论做成一张可对照的表。
- 必须讲清：**WAL 保证的是不丢与可恢复，growing/sealed 保证的是实时与吞吐；一致性级别调的是「能不能马上看到」，不是「数据对不对」。**
- 标注示意：网络跳数与落盘耗时是模型化的数值，不是实测。

### 站 6 · 查询向量化

- 输入框 + 6 个预设问题（见第六节），选中后展示：问题 → 向量 → 与库中 Top-1 的相似度。
- 必须出现「同一个模型、同一个维度」的约束：换模型/换维度就得重建集合，页面用一次「故意改维度 → 检索报错」的对照说明。
- 可调：`limit`、`ef` / `nprobe`。
- 真算：Top-k 列表与相似度分数。

### 站 7 · 检索路由

把 `architecture_overview.md` 的 Search 数据流画成时序图，并让它可以「走一遍」：

```
SDK → Proxy（命中路由缓存，不惊动 Coordinator）
     ├→ Streaming Node：查 growing 数据
     └→ Query Node：从对象存储加载 sealed segment，做段内检索
                    ↓ 段级归并
         Streaming Node 归并各 Query Node 的结果
                    ↓
         Proxy 做最终归并 → 客户端
```

- 可调：数据分布（growing 与 sealed 的比例）、查询节点数量。
- 真算：三级归并的中间结果 —— 展示「各分片 Top-k」如何合成「全局 Top-k」，并证明中间结果不能简单拼接。
- 必须讲清：**归并发生在三个层级，每一层都只保留 Top-k，所以 k 与各层候选数会共同决定最终召回。**

### 站 8 · 过滤与分区

- 过滤器构造器：`dept`、`updated`、`acl` 三个条件，表达成 Milvus 的过滤表达式（展示原文，如 `dept == "finance" and updated >= 1760000000`）。
- 同一句查询，切换**先过滤（pre-filter）**与**后过滤（post-filter）**，看结果集怎么塌掉：后过滤是先取 Top-k 再筛，筛完可能一条不剩。
- 真算：两种策略下的结果条数与命中率。
- 必须出现多租户口径：隔离粒度是 database / collection / partition / partition key，**隔离级别越高越安全，也越贵**；用一张小表说明选择依据。

### 站 9 · 混合检索

- 两路并排：dense（语义）与 BM25（字面）。各显示自己的 Top-5 与分数（dense 显示距离，BM25 显示相关性分数，别混为一谈）。
- 中间是融合：展示 `AnnSearchRequest` 两段配置 + `hybrid_search` 调用 + ranker（`WeightedRanker` 或 RRF）。权重可拖动。
- 真算：两路名次 → 融合名次，逐条对照；并给出一个**「向量排错、BM25 排对」**的问题（精确编号类），让融合的价值肉眼可见。
- 必须讲清：BM25 这一路由 Milvus 内置 Function 完成（`VARCHAR` + `enable_analyzer=True` → 稀疏向量 → `SPARSE_INVERTED_INDEX`），所以这条链路应用侧**不需要**再调 embedding 模型。

### 站 10 · 重排、上下文与生成

- 重排开关：关掉时用融合顺序，打开后按重排分数重排，显示名次变化与「为什么这条被提上来」。
- 上下文预算条：Top-n 条拼成 prompt，显示 token 数（估算，标注口径）、超预算时如何截断。
- 引用：每个句子标注来源块编号，点击可跳回站 1 的块。
- 拒答：最高分低于阈值时拒答，阈值可调 —— 调到很低时，让页面真的「硬答」一次，并标出不支持的句子。
- 必须讲清：重排与生成都在应用侧（PyMilvus 提供 reranker 集成，但不是 Milvus 内核的检索能力）。

## 五、「真算」和「示意」必须分开

页面里所有数字分两类，每站右上角用徽章标出来，页脚放一张汇总表说明哪些是模型化的：

**必须真算（有实现、有测试）**

- 切分统计：块数、长度分布、实际重叠
- 余弦 / 内积，归一化前后的排序对照
- BM25：词元、df、IDF、单条得分
- 向量检索：真实实现的 HNSW 或 IVF，输出访问点数与 recall@k
- 三级归并：分片 Top-k → 全局 Top-k
- 过滤：pre-filter 与 post-filter 的结果差异
- 融合：加权与 RRF 的排名计算
- 重排打分、token 估算、引用命中率

**只能示意（必须显式标注「示意」）**

- 分布式调度、网络跳数、WAL 落盘与 compaction 的耗时
- 真实 QPS、延迟、内存占用曲线（只允许给「量级示意」并说明假设）
- 示意向量与真实 embedding 的差距
- 官方 benchmark 里的倍数（2-5x、30%-70%）如要引用，必须写清「官方 benchmark，非本页实测」

标注方式统一：一个 ⓘ 角标 + 悬停/聚焦浮层 + 页脚汇总，不要只在某一段落里口头说一句。

## 六、语料、预设问题与数字口径

**语料自造**：5 篇虚构的《VectorOps 向量库产品知识库》文档（部署规格、索引选型、权限与加密、计费、故障码），界面里明确写「虚构语料，仅用于演示检索行为，不是 Milvus 官方文档」。

为什么自造：需要可控地制造「语义近但字面远」「编号精确」「跨文档」「无答案」这几类情形，同时避免直接搬官方文档。

**6 个预设问题**（每个都要在同一批语料上跑出不同结论）：

1. 语义改写：问「合同到期后数据还能留多久」，语料里写的是「保留期限」，字面对不上、语义对得上。
2. 精确编号：问「VX-2048 是什么错误」，BM25 一击即中，向量在相似编号之间摇摆。
3. 跨文档：问「M 调大之后内存和召回怎么变」，答案横跨索引与计费两篇。
4. 权限：只保留 `acl` 允许 finance 的块，验证过滤时机。
5. 无答案：问「明年会不会涨价」，验证拒答阈值。
6. 时间条件：只保留 `updated >= 2026-01-01` 的块，验证过滤与召回同时变化。

**数字口径**

- 所有汇总数字（块数、文档数、向量维度、候选数、token 数）由数据实时计算，禁止写死。
- 页面出现的每个 Milvus 参数都要标出「文档出处」或「示意」，两者不能混着写。
- 数据文件里的每条语料带 `source / dept / version / updated / acl`，站 8 的过滤就靠它们。

## 七、视觉方向

**不要做成 rag-viz 那样深色控制台**（同一仓库里已经有一页了），这一页走**工程蓝图 / 数据流仪表盘**的路子：

- 底色浅色纸感（近 `#F2F4F6`），主线条石墨色，强调色一蓝一青（用于「应用侧 / Milvus 侧」两条泳道），警示色用于「示意」和「事故」。
- 版面主体是**横向泳道**：应用侧 | Milvus 接入层 | 执行节点 | 存储与索引文件，站点内容挂在泳道里，读起来像一张会动的架构图。
- 顶部十站进度轨道，已走过/当前/未到的状态要清楚，不只是换个颜色。
- 数字用等宽字体，标签用系统无衬线字体，中文标题可以用衬线字体制造「文档感」。
- 动效克制：只做「数据在泳道里移动」「重排名次交换」这类有信息量的动画；`prefers-reduced-motion` 下全部降级为静态。
- 明确避开：紫色渐变、满屏发光、圆角卡片堆叠、每个区块都配一个大图标。

**首屏文案（可直接用）**

- 眉标：`MILVUS × RAG · EXECUTION TRACE`
- 主标题：**一条查询，穿过 Milvus 的十站**
- 副标题：从一句提问，到 LLM 手里那段带引用的上下文 —— 中间哪一段是 Milvus 干的，哪一段不是。
- 主按钮：开始追踪 / 直接看结论

**结论卡（首屏下方必放）**：三句话讲清边界 ——

1. Milvus 存向量、建索引、做检索与融合，**不生成 embedding，也不写答案**。
2. 写入走 Streaming Node 与 WAL，查询走 Query Node 与对象存储，两条路在 Proxy 汇合。
3. 过滤、混合检索、重排是三种不同的能力，别把它们当成一件事。
